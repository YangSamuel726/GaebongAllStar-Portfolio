### 문제 해결 요약
- 캐릭터나 무기를 따라다니는 SFX/VFX를 재생하기 위해, 재생 요청에 추적 대상의 NetworkBehaviourId를 포함했습니다. 각 클라이언트는 해당 ID로 로컬의 대상 컴포넌트를 조회하고, 이펙트를 그 하위에 배치하여 대상의 이동을 따라가도록 구성했습니다.

### 1. 요구 사항
- 이 프로젝트의 SFX/VFX는 `NetworkBuffer`를 통해 재생 요청을 전달하고, 각 클라이언트에서 로컬 객체로 재생하는 구조입니다.
고정된 위치에서 재생하는 이펙트는 요청에 월드 좌표를 포함하면 됩니다. 그러나 캐릭터나 무기를 따라다니는 이펙트는 재생을 시작한 이후에도 대상의 이동을 따라가야 합니다.
- 예를 들어 무기에 힘을 모으는 차징 이펙트는 무기가 움직여도 무기에 붙어 있어야 합니다. 재생 시작 시점의 좌표만 전달하면, 대상이 이동했을 때 이펙트는 처음 위치에 남게 됩니다.

(공란: 레프록시 차징 이펙트 GIF)

- 이를 위해 재생 요청에 어디에서 재생할지뿐 아니라, 어떤 대상을 계속 따라갈지를 표현할 수 있어야 했습니다.

### 2. 해결 과정
#### 추적 대상을 ID로 전달
- 각 클라이언트에 존재하는 캐릭터와 무기는 서로 별개의 로컬 객체입니다. 따라서 한 클라이언트의 객체 참조를 다른 클라이언트에서 그대로 사용할 수는 없습니다.
- 이 문제를 해결하기 위해 Fusion의 `NetworkBehaviourId`를 사용했습니다. 이 ID는 같은 세션의 각 클라이언트에서 대응되는 `NetworkBehaviour`를 식별할 수 있는 값입니다.
- 이펙트가 따라갈 위치에는 `NetworkLocationRegister`를 배치하고, 재생 요청에 이 컴포넌트의 ID를 포함했습니다. 고정 위치에 재생하는 요청은 좌표를 사용하고, 특정 대상을 따라가는 요청은 대상의 ID를 사용하도록 구분했습니다.

(공란: 고정 좌표 요청과 추적 대상 ID 요청을 비교하는 코드)

#### ID로 로컬 대상을 조회
- 재생 요청을 받은 클라이언트에서는 ID에 대응하는 로컬 객체의 `Transform`이 필요했습니다. 당시에는 Fusion의 내장 조회 기능을 활용하지 못해, ID와 객체 참조를 연결하는 별도의 저장소를 구현했습니다.

```csharp
Dictionary<NetworkBehaviourId, NetworkLocationRegister>
```
- 조회 기준이 ID였으므로, ID를 키로 사용해 대상 참조를 가져올 수 있는 Dictionary를 선택했습니다.

- `NetworkLocationRegister`는 `Spawned()`에서 자신의 생성을 알리고, 저장소는 해당 컴포넌트를 등록합니다. `Despawned()`에서는 제거를 알려 더 이상 존재하지 않는 대상을 저장소에서 제외합니다.
(공란: Spawned·Despawned의 알림과 저장소 등록·제거 코드)

- 이후 `NetworkBuffer`는 저장소에 대상 ID를 전달하여, 해당 클라이언트에 존재하는 추적 대상의 `Transform`을 가져옵니다.
(공란: 대상 ID로 Transform을 조회하는 코드)

#### 로컬 이펙트를 추적 대상에 연결
- 대상을 찾으면 풀에서 이펙트 객체를 가져와 대상의 자식으로 배치하고, 기준 위치에 맞춰 재생합니다.

- 각 클라이언트가 같은 ID에 대응하는 대상을 찾아 연결하므로, 로컬 이펙트는 각 화면에서 해당 캐릭터나 무기의 이동을 따라갑니다. 이펙트 자체의 위치를 계속 동기화하는 대신, 추적 대상의 이동을 활용하는 구조입니다.

(공란: 동일한 대상 ID가 클라이언트 A·B의 대상 객체로 연결되는 다이어그램)

### 3. 한계 및 회고
- 이 구조는 이펙트의 추적 대상을 일치시키지만, 모든 클라이언트의 월드 좌표를 같은 순간에 완전히 일치시키지는 않습니다. 이펙트가 따라가는 움직임은 대상 객체의 위치 동기화와 각 클라이언트의 표시 상태에 영향을 받습니다.

- 또한 ID를 전달받았다고 해서 해당 대상이 반드시 로컬에 존재하는 것은 아닙니다. 현재 구현에서는 대상을 찾지 못하면 해당 재생 요청을 실패 처리합니다. 대상이 준비될 때까지 기다리거나 재시도하는 처리는 별도의 보완 과제입니다.

- 구현 이후에는 Fusion이 `Runner.TryFindBehaviour()`를 통해 ID에 대응하는 로컬 컴포넌트 조회를 제공한다는 것을 확인했습니다. 현재는 직접 만든 저장소에서 조회하지 못했을 때 이 기능을 사용하고 있습니다.

(공란: Runner.TryFindBehaviour() 조회 코드)

- 이를 통해 별도로 구현했던 등록·조회 구조를 내장 기능으로 단순화할 수 있음을 확인했습니다. 이후 비슷한 기능을 설계할 때는 필요한 동작을 먼저 정리하고, 프레임워크가 이미 제공하는 기능과 직접 구현해야 할 부분을 구분해야 한다는 점을 배웠습니다.
