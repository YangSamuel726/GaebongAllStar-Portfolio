### 1. 게임의 형태와 요구 사항
- GaebongAllStar에는 기절, 매혹, 침묵, 사망 등 다양한 상태가 존재합니다. 플레이어가 캐릭터를 움직이거나 스킬을 사용할 때 시스템은 현재 캐릭터의 상태를 기반으로 움직일 수 있는지, 스킬을 사용할 수 있는지 등 여부를 결정합니다. 상태는 초기 몇 가지로만 한정되어지지 않고 기획에 따라 계속해서 종류가 늘어납니다.

### 2. 이전 구현과 한계
변경 전 상태 로직 일부
  (상태의 상위분류를 조건문으로 나타내는 코드 예시)
  (코드 원본 링크)

- 초기에는 캐릭터의 상태를 enum과 개별 변수로 관리했습니다. 상태가 변경되면 이벤트로 상태 종류와 변경 값을 전달했고, 이동·애니메이션·스킬처럼 해당 상태가 필요한 기능들이 이벤트를 받아 각자의 조건문에서 처리했습니다.<br>
- 상태가 적을 때는 단순한 방식이었지만, 캐릭터와 스킬이 늘면서 문제가 생겼습니다. 새로운 상태를 추가할 때마다 그 상태의 영향을 받는 기능을 찾아 조건을 추가하거나 수정해야 했습니다. 그 결과 하나의 상태 변경이 여러 스크립트의 수정으로 이어졌습니다.<br>
- 상태 사이의 분류 관계도 코드에 직접 작성되어 있었습니다. 예를 들어 기절과 강제 이동은 모두 캐릭터의 행동을 제한하는 HardCC 상태에 속하지만, 이러한 관계가 데이터로 정의된 것이 아니라 기절 중이거나 강제 이동 중이면 HardCC라는 조건문으로 구현되어 있었습니다. 같은 분류의 상태가 추가될 때마다 이 조건문도 함께 수정해야 했습니다.<br>
- 상태가 늘어날수록 각 코드가 더 많은 상태의 종류와 관계를 알아야 했고, 상태 시스템과 이동·스킬·애니메이션 코드의 결합도도 함께 높아졌습니다.

### 3. 해결 목표와 설계 조건
  1. 같은 분류의 상태가 추가되어도 기존 조건 검사를 유지할 수 있어야 한다.
  2. 모든 클라이언트가 동일한 캐릭터 상태를 확인할 수 있어야 한다.
  4. 상태의 상하위 관계를 코드 밖에서 명시적으로 정의할 수 있어야 한다.

### 4. 선택한 구조와 동작 흐름
#### 4-1 상태를 에셋으로 정의
- 캐릭터의 각 상태를 TagSO라는 ScriptableObject 에셋으로 표현했습니다. 각 상태 에셋은 네트워크에서 상태를 식별하기 위한 고유 ID를 가지며, 상위 분류가 있다면 부모 상태 에셋을 참조합니다.
- 예를 들어 기절과 강제 이동 상태의 부모를 HardCC로 설정하면, 두 상태가 모두 행동을 제한하는 상태라는 관계를 에셋에서 명시할 수 있습니다. 기존처럼 코드에 기절 중이거나 강제 이동 중이면 HardCC라는 조건문을 작성할 필요가 없습니다.<br>

(태그 계층 구조를 보여주는 이미지) + (태그 에셋 하나 상세 내용보여주기)<br>

#### 4-2 ID를 이용한 네트워크 상태 동기화
- 게임 실행 중에는 상태 에셋 자체를 전송하지 않고, 상태의 ID와 활성화 횟수를 네트워크로 동기화합니다. 각 클라이언트는 동일한 ID를 통해 어떤 상태가 활성화됐는지 확인합니다. 이동·스킬·애니메이션처럼 상태를 사용하는 기능은 필요한 개별 상태나 상위 분류 상태를 참조하여 조건을 검사합니다.<br>

(Tag System 스크립트 보여주기)

#### 4-3 새로운 상태를 추가하는 과정
- 새로운 상태가 기존 분류에 속한다면 상태 에셋을 생성하고 부모를 지정하는 것으로 계층에 추가할 수 있습니다. 상위 상태를 검사하던 기존 기능은 새로운 하위 상태를 자동으로 같은 분류로 인식하므로, 공통 조건 코드를 수정하는 범위를 줄일 수 있습니다.
