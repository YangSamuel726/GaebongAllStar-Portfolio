### 1. 게임의 형태와 요구 사항
- `GaebongAllStar`에는 기절, 매혹, 침묵, 사망 등 다양한 상태가 존재합니다. 플레이어가 캐릭터를 움직이거나 스킬을 사용할 때 시스템은 현재 캐릭터의 상태를 기반으로 움직일 수 있는지, 스킬을 사용할 수 있는지 등 여부를 결정합니다. 상태는 초기 몇 가지로만 한정되어지지 않고 기획에 따라 계속해서 종류가 늘어납니다.

### 2. 이전 구현과 한계
**변경 전 상태 로직 일부**
```csharp
    bool CheckHardCC() // 캐릭터가 하드CC 상태인지 확인하는 함수
    {
        if (_isStunned || _isForceMoved)
        {
            return true;
        }
        else
        {
            return false;
        }
    }
```

- 초기에는 캐릭터의 상태를 enum과 개별 변수로 관리했습니다. 상태가 변경되면 이벤트로 상태 종류에 따른 enum값을 전달했고, 이동·애니메이션·스킬처럼 해당 상태가 필요한 기능들이 이벤트를 받아 각자의 조건문에서 처리했습니다.
- 상태가 적을 때는 단순한 방식이었지만, 캐릭터와 스킬이 늘면서 문제가 생겼습니다. 새로운 상태를 추가할 때마다 그 상태의 영향을 받는 기능을 찾아 조건을 추가하거나 수정해야 했습니다.
- 상태 사이의 분류 관계도 코드에 직접 작성되어 있었습니다. 예를 들어 기절과 강제 이동은 모두 캐릭터의 행동을 제한하는 HardCC 상태에 속하지만, 이러한 관계가 데이터로 정의된 것이 아니라 기절 중이거나 강제 이동 중이면 HardCC라는 조건문으로 구현되어 있었습니다. 같은 분류의 상태가 추가될 때마다 이 조건문도 함께 수정해야 했습니다.
- 결과적으로 상태의 수가 증가할수록 각 기능이 더 많은 상태의 종류와 관계를 알아야 했으며, 상태 간의 관계가 여러 코드에 분산되어 전체 구조를 한눈에 파악하기 어려워졌습니다. 또한 하나의 상태 변경이 여러 기능의 수정으로 이어지면서 시스템 간 결합도와 유지보수 비용도 함께 증가했습니다.
- 동일한 상태가 여러 원인에 의해 동시에 적용되는 경우를 안전하게 처리하기 어려운 문제도 있었습니다. 예를 들어 한 로직이 Stun을 적용한 뒤 2초 후 제거하고, 다른 로직이 같은 Stun을 적용한 뒤 4초 후 제거하도록 요청하는 경우, 먼저 실행된 제거 요청에 의해 상태 자체가 해제될 수 있었습니다. 이 때문에 동일 상태의 중첩 적용과 각 적용 주기의 독립적인 종료를 보장할 수 없었습니다.

### 3. 해결 목표와 설계 조건
  1. 같은 분류의 상태가 추가되어도 기존 조건 검사를 유지할 수 있어야 한다.
  2. 네트워크에서 동일한 상태를 공유할 수 있어야 한다.
  3. 동일 상태의 중첩 적용을 처리할 수 있어야 한다.
  4. 상태의 상하위 관계를 코드 밖에서 명시적으로 정의할 수 있어야 한다.

### 4. 선택한 구조와 동작 흐름
#### 4-1 상태를 에셋으로 정의
- 캐릭터의 각 상태를 `TagSO`라는 ScriptableObject 에셋으로 표현했습니다. 각 상태 에셋은 네트워크에서 상태를 식별하기 위한 고유 ID를 가지며, 상위 분류가 있다면 부모 상태 에셋을 참조합니다.
- 예를 들어 기절과 강제 이동 상태의 부모를 HardCC로 설정하면, 두 상태가 모두 행동을 제한하는 상태라는 관계를 에셋에서 명시할 수 있습니다. 기존처럼 코드에 기절 중이거나 강제 이동 중이면 HardCC라는 조건문을 작성할 필요가 없습니다.
- 상태 에셋의 부모 참조에 따른 관계를 한눈에 볼 수 있도록 구현하여 누구라도 쉽게 상태 관계를 이해할 수 있도록 하였습니다.

#### 4-2 ID를 이용한 네트워크 상태 동기화 / Dictionary를 사용한 중첩 적용
- 게임 실행 중에는 `TagSO` 에셋 자체를 네트워크로 전달하지 않고, Tag의 고유 ID와 활성화 횟수를 `NetworkDictionary<int, int>`에 저장하여 동기화합니다. 각 클라이언트는 동일한 ID를 기준으로 현재 활성화된 상태를 확인할 수 있습니다.
- 자식 Tag가 활성화되면 해당 Tag의 부모도 재귀적으로 활성화합니다. 예를 들어 Stun이 활성화되면 부모인 HardCC 역시 활성 상태가 되므로, 이동·스킬·애니메이션 등의 기능은 개별 상태를 모두 알 필요 없이 HardCC의 활성 여부만 검사할 수 있습니다.

```csharp
    [Networked, Capacity(GameConfig.AllTagCount)] private NetworkDictionary<int, int> TagDictionary { get; } // id, 활성화 count

    public void AddTag(int tag)
    {
        if (Object.HasStateAuthority == false) return;
        if (tag == TagUtil.INVALID_TAG_ID) return;
        if (tag == TagUtil.NO_PARENT_TAG_ID) return;

        if (TagDictionary.TryGet(tag, out int currentCount))
        {
            TagDictionary.Set(tag, currentCount + 1);
        }
        else
        {
            TagDictionary.Set(tag, 1);
            InvokeTagAddedEvent(tag);
        }
        AddTag(parentTagMap[tag]);
    }

    public bool HasTag(int tag)
    {
        return TagDictionary.TryGet(tag, out int count) && count > 0;
    }
```

#### 4-3 새로운 상태를 추가하는 과정
- 새로운 상태가 기존 분류에 속한다면 새로운 `TagSO`를 생성하고 부모 Tag를 지정하는 것으로 계층에 추가할 수 있습니다.
- 기존 기능이 HardCC와 같은 상위 Tag를 기준으로 조건을 검사하고 있다면, 새로운 하위 상태가 추가되어도 해당 기능의 조건문을 수정할 필요가 없습니다. 이를 통해 상태 종류가 증가할 때 기존 코드로 변경이 전파되는 범위를 줄였습니다.


### 5. 결과
- 기존에는 각 상태마다 네트워크 변수를 따로 할당하고 새로운 상태를 생성하거나 상위 분류를 표현하기 위해 코드를 수정해야 했습니다. 변경 후에는 코드를 수정할 필요없이 에셋을 추가하고 ID와 부모 Tag를 설정해 주면 끝이났습니다.

#### 5-1 회고
- 계층형 Tag 구조를 통해 상태 간 관계와 조건 검사를 단순화할 수 있었지만, Tag ID와 부모 관계의 정합성을 별도로 보장해야 하는 문제가 생겼습니다. 이를 위해 이후에는 Tag 생성 및 관리 과정을 Editor Tool로 통합해 데이터의 고유성과 계층 관계를 관리하도록 개선했습니다.
