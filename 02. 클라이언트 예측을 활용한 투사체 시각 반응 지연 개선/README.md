### 문제 해결 요약
- 플레이어가 발사 입력을 했을 때 투사체가 늦게 나타나면 조작에 대한 반응이 둔하게 느껴질 수 있습니다. 네트워크 지연이 있는 환경에서도 빠른 시각적 피드백을 제공하기 위해, 네트워크 오브젝트 기반 투사체와 데이터 기반 로컬 투사체의 입력 반응 지연을 비교했습니다.
- 두 네트워크 환경에서 예측 적용 여부를 포함한 여섯 가지 조건을 각각 50회씩 측정했습니다. 지연 환경에서 데이터 기반 투사체에 클라이언트 예측을 적용한 결과, 입력부터 표시 준비 완료까지의 평균 지연이 예측 미적용 대비 **221.55ms**에서 **21.68ms**로 약 **90.2%** 감소했습니다.

### 1. 요구 사항과 비교 대안
- 투사체는 플레이어의 입력 결과를 직접 보여주는 요소입니다. 발사 입력과 투사체 표시 사이에 지연이 발생하면, 플레이어는 입력이 정상적으로 처리됐는지 즉시 확인하기 어렵습니다. 따라서 네트워크 환경에서도 서버의 최종 판단을 유지하면서, 발사한 플레이어에게는 빠른 시각적 반응을 제공하고자 했습니다.
- 투사체 구현 방식으로 다음 두 가지를 비교했습니다.

| 구현 방식 | 동작 |
|---|---|
| 네트워크 오브젝트 기반 | 서버에서 투사체를 네트워크 오브젝트로 생성하고, 클라이언트가 생성 정보를 전달받아 표시합니다. |
| 데이터 기반 로컬 객체 | 투사체를 표현하는 데이터를 네트워크 상태로 관리하고, 각 클라이언트에서 해당 데이터를 바탕으로 로컬 시각 객체를 표시합니다. |

- 데이터 기반 방식은 서버 데이터를 받은 뒤 표시하는 경우와 클라이언트가 입력을 예측 처리하여 먼저 표시하는 경우로 나누었습니다. 이를 통해 객체 표현 방식의 차이와 클라이언트 예측의 효과를 구분해서 확인했습니다.


### 2. 데이터와 시각 객체의 분리
- 데이터 기반 방식에서는 발사 위치·방향 등 투사체를 표현하는 데이터를 관리하고, 클라이언트의 표시 과정에서 풀에 보관된 로컬 객체를 가져와 활성화하도록 구성했습니다.
- 클라이언트 예측을 적용한 경우에는 입력을 먼저 처리한 결과를 바탕으로 투사체를 표시합니다. 이후 서버 상태를 수신하면 네트워크 상태는 재시뮬레이션을 통해 갱신되고, 시각 객체는 갱신된 데이터를 바탕으로 표시됩니다.
- 이 구조의 목적은 서버의 최종 판단을 기다리는 시간과 플레이어에게 첫 시각적 피드백을 제공하는 시간을 분리하는 것입니다. 로컬 투사체를 먼저 표시하는 것이 서버의 충돌·피해 판정까지 확정한다는 의미는 아닙니다.


### 3. 측정 방법
- 플레이어가 경험하는 입력 반응을 비교하기 위해, 서버와 클라이언트의 시각을 비교하지 않고 입력한 클라이언트 내부에서 두 시점을 기록했습니다.
> 시작 : 플레이어의 발사 입력을 감지한 시점<br>
> 종료: 해당 투사체의 초기화와 시각적 활성화 준비가 완료된 시점

- 네트워크 오브젝트 방식은 클라이언트의 스폰 초기화 완료 지점을, 데이터 방식은 로컬 투사체의 `Activate()` 완료 지점을 기준으로 삼았습니다.

- 시간은 `Stopwatch.GetTimestamp()`로 기록하고 다음 식으로 밀리초로 환산했습니다.
```csharp
double delayMs =
    (spawnTimestamp - inputTimestamp)
    * 1000.0 / Stopwatch.Frequency;
```

- 추가 지연이 없는 환경과 네트워크 상태를 악화시킨 환경에서 세 가지 방식을 각각 50회씩, 총 300회 측정했습니다.

| 환경 | 설정 |
|---|---|
| 추가 지연 없음 | 인위적인 네트워크 지연·손실 시뮬레이션 비활성화 |
| 지연 환경 | 기본 지연 150ms, 추가 지터 최대 50ms, 패킷 손실 확률 5% |


### 4. 측정 결과
- 다음은 각 조건의 측정 결과입니다. 높은 지연이 발생한 기록도 제외하지 않고 포함했습니다.

| 환경 | 방식 | 평균 | 중앙값 | P95 |
|---|---|---:|---:|---:|
| 추가 지연 없음 | 네트워크 오브젝트 | 49.65ms | 49.36ms | 59.44ms |
| 추가 지연 없음 | 데이터 · 예측 X | 37.26ms | 35.41ms | 47.29ms |
| 추가 지연 없음 | 데이터 · 예측 O | **20.67ms** | **20.73ms** | **28.81ms** |
| 지연 환경 | 네트워크 오브젝트 | 223.45ms | 216.06ms | 231.48ms |
| 지연 환경 | 데이터 · 예측 X | 221.55ms | 221.68ms | 239.49ms |
| 지연 환경 | 데이터 · 예측 O | **21.68ms** | **22.01ms** | **29.36ms** |

- 각 조건은 50회이며, P95는 측정값을 오름차순으로 정렬한 뒤 48번째 값을 사용했습니다.
- 추가 지연이 없는 환경에서는 예측 없는 데이터 방식이 네트워크 오브젝트 방식보다 평균 약 12.39ms 빨랐습니다. 그러나 지연 환경에서는 두 방식 모두 평균 약 222ms가 소요됐습니다. 로컬 객체를 사용하더라도 표시할 데이터를 서버에서 기다린다면 네트워크 지연의 영향을 크게 받는다는 결과였습니다.
- 반면 데이터 방식에 예측을 적용하자, 지연 환경의 평균 반응 지연이 221.55ms에서 21.68ms로 약 199.88ms 감소했습니다. 중앙값과 P95에서도 큰 차이가 나타났으며, 50회 모두 약 12~30ms 범위에 있었습니다.
- 예측을 적용한 방식은 추가 지연이 없는 환경에서 평균 20.67ms, 지연 환경에서 평균 21.68ms로, 두 환경 사이의 평균 차이도 약 1.01ms였습니다.


### 5. 기술 선택과 판단
- 이번 비교에서 빠른 시각 반응에 크게 기여한 요소는 데이터 기반 표현에 클라이언트 예측을 적용하여 서버 응답 전에 투사체를 표시한 것이었습니다.
- 따라서 이 프로젝트의 발사 입력에 대한 즉각적인 피드백 요구에는 데이터 기반 로컬 투사체와 클라이언트 예측의 조합이 적합하다고 판단했습니다. 데이터 방식 자체가 항상 더 우수하다고 결론 내리기보다, 구현 방식과 예측 적용 여부를 분리해서 측정함으로써 선택의 근거를 확인했습니다.


### 6. 한계 및 회고
- 이번 측정은 입력 감지부터 코드상 투사체 표시 준비 완료까지를 대상으로 합니다. 입력 장치의 감지 지연이나 렌더링·모니터 출력에 걸리는 시간은 포함하지 않았으므로, 실제 화면에 보이기까지의 전체 지연과는 차이가 있습니다.
- 또한 최초 시각 반응이 빨라졌다고 해서 서버의 충돌·피해 판정까지 빨라진 것은 아닙니다. 예측과 서버 결과가 다를 때 발생하는 보정이나 시각적 불연속도 별도로 평가해야 합니다.
- 각 조건을 50회 측정한 결과는 해당 테스트 환경에서의 경향을 보여줍니다. 모든 네트워크 환경에서 동일한 결과를 보장하거나, 시각적 품질 전체가 개선됐다고 판단할 수는 없습니다.
- 이번 실험을 통해 구현 방식의 장점을 설명하는 것뿐 아니라, 플레이어가 경험하는 구간을 측정 기준으로 정하고 대안을 비교하는 과정이 기술 선택의 근거가 된다는 점을 확인했습니다.
